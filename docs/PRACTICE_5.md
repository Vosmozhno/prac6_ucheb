## Таблица прав

Серверные операции и адреса интерфейса перечислены отдельно: у каждой роли есть собственный экран. Администратор сохраняет права API старшей роли из исходного контракта; рабочее место /loans в интерфейсе выделено библиотекарю.

|---|---|---|---|
| Просмотр каталога и справочников | Да | Да | Да |
| Создание, изменение, логическое и массовое удаление каталога | Нет | Да | Да |
| Общий список читателей и работа с билетами | Нет | Да | Да |
| Экран /my-loans, собственные выдачи и продление | Да | Нет | Нет |
| Экран /loans, рабочее место библиотекаря | Нет | Да | Нет |
| Оформление выдачи из карточки книги | Нет | Да | Да |
| Операция API закрытия выдачи | Нет | Да | Да |
| Физическое удаление и восстановление | Нет | Нет | Да |
| /admin/users, просмотр пользователей и изменение роли | Нет | Нет | Да |
| /admin/stats, статистика | Нет | Нет | Да |

Читатель не может расширить выборку параметром readerId: сервер сам подставляет ограничение текущего пользователя. GET /readers доступен ему только для собственной карточки, а интерфейс общего списка читателей закрыт. Изменение собственной роли запрещено, исходная запись администратора защищена от потери доступа.

## Жизненный цикл сессии

1. POST /auth/register создаёт пользователя reader, связанного читателя и билет. Роль из тела регистрации не принимается как право. После регистрации пользователь переходит на вход.
2. POST /auth/login возвращает access, refresh и пользователя. Пароль используется только для запроса; токены, пользователь и временные отметки сохраняются в localStorage через shared_preferences.
3. После перезагрузки GET /auth/me проверяет access и получает актуальную роль. Если access истёк, выполняется POST /auth/refresh. При временной недоступности сервера сохранённые данные не уничтожаются только из-за ошибки соединения.
4. Защищённые запросы содержат Authorization: Bearer. При 401 вне /auth/* выполняется один общий refresh; успешный ответ заменяет пару токенов и позволяет повторить исходный запрос один раз. Ошибки входа, 403 и неудачный refresh не запускают рекурсию.
5. Выход, 180 секунд неактивности или общий предел 1800 секунд удаляют локальную сессию. Refresh отзывается через /auth/logout. Время начала не меняется при refresh и перезагрузке, последний ввод также сохраняется. Истёкшая сессия выводит даже из формы с несохранёнными данными.

Access на сервере по умолчанию живёт 900 секунд, refresh — неделю. Для проверки запущен --ttl 60. Выход отзывает refresh и удаляет локальный access; ранее выданный access остаётся действителен на сервере до своего срока истечения. Пароль проверяет сервер, клиент его не хеширует. Локальный стенд работает по HTTP на localhost; при размещении вне локального стенда передача пароля требует HTTPS.

Подтверждённая последовательность в журнале рабочего API:

```text
POST /api/loans/1/renew → 401
POST /api/auth/refresh → 200
POST /api/loans/1/renew → 200
```

Продление выполнилось один раз, повторный вход не потребовался. Полный фрагмент: [practice5/refresh-check.txt](practice5/refresh-check.txt).

Неудачное обновление проверено отдельными тестами: один запрос /auth/refresh, выход и очистка localStorage, без повторения исходного запроса после отказа. Также проверен случай, когда повторный запрос снова возвращает 401: повторов исходного запроса не больше двух, повторного refresh нет. Запоздалый ответ refresh после выхода не восстанавливает сессию.

## Проверка клиентской защиты

В обычной сборке роль восстанавливается с сервера через /auth/me, поэтому простая правка кэша пользователя не повышает роль после перезагрузки. Для требуемого опыта добавлен отдельный, выключенный по умолчанию параметр AUTH_ROLE_DEMO=true. Он разрешает подменять только отображаемую роль из дополнительного ключа. Сервер, токен и серверные права не меняются.

Последовательность опыта:

1. Запускаем учебную сборку с --dart-define=AUTH_ROLE_DEMO=true и входим reader / reader123.
2. Открываем DevTools → Application → Local storage → http://localhost:5555. Добавляем flutter.auth_ui_role со значением "admin" — именно JSON-строку с кавычками.
3. Обновляем страницу. Имя остаётся «Смирнов П. А.», а интерфейс показывает роль администратора, разделы пользователей и статистики. Появляется поясняющий баннер учебной демонстрации.
4. Нажимаем административный раздел пользователей. Настоящий GET /api/users получает 403 Forbidden; в приложении отображается отказ, данные пользователей не загружаются.
5. После проверки завершаем сессию и запускаем обычную сборку без AUTH_ROLE_DEMO. Дополнительный ключ удаляется при выходе и новом входе.

Смысл проверки: пользователь может изменять localStorage, JavaScript и интерфейс своего браузера. Появившаяся кнопка и успешно пройденный клиентский redirect не доказывают наличие права. Сервер проверяет подпись токена и находит действующую учётную запись; у неё по-прежнему роль reader. Поэтому операция отклоняется. Ключ auth_ui_role сервер вообще не получает. Подмена содержимого самого подписанного токена — другой опыт: она нарушает подпись и даёт 401.

Токены на снимке Application скрыты фильтром auth_ui_role. Снимки DevTools получены в Chrome; основные экраны приложения — во встроенном браузере без указателя мыши.
