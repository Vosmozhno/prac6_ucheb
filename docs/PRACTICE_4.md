# Практическая работа №4. Подключение REST API

Цель: перевести приложение ПР3 на работу с REST API, освоить Dio для Flutter Web, диагностику CORS и обработку сетевых состояний.

## Ход работы

1. Продолжаем проект prac2 и подключаем Dio в pubspec.yaml. Копируем учебный сервер и контракт в папку api, запускаем сервер и проверяем GET /api/__health.
2. В lib/core/config.dart задаём адрес через String.fromEnvironment. Фактический API_BASE_URL передаём параметром --dart-define, клиент запускаем на фиксированном порту 5555.
3. В lib/core/api_client.dart создаём Dio с таймаутами и общим интерсептором. Добавляем Bearer-токен при наличии сессии; в отладке выводим метод, адрес и статус каждого запроса.
4. В lib/core/api_exceptions.dart преобразуем HTTP-коды и DioException в собственные исключения. Функция guard сохраняет уже разобранные ошибки, поэтому 422 не теряет словарь полей.
5. В lib/repositories/api_entity_repository.dart реализуем общие операции API. Книги и авторы используют прежние интерфейсы; жанры, издательства и читатели — тот же EntityRepository.
6. Передаём поиск, фильтры, сортировку, page и size на сервер. Клиент показывает полученную страницу; новый переход по страницам вызывает отдельный GET.
7. Добавляем CancelToken для запросов списков. Изменение строки поиска отменяет предыдущий запрос сразу, а задержка 400 мс ограничивает частоту отправки новых запросов.
8. Создаём ApiReferenceCache для авторов, жанров и издательств. Одновременные обращения используют одну загрузку, повторное открытие форм использует кэш, успешные изменения обновляют его.
9. Обрабатываем серверные ошибки 422 через состояние формы и существующий validator. Пока выполняется сохранение, кнопка и поля заблокированы; повторное нажатие не создаёт дополнительный POST.
10. Добавляем вход в учебный API и экран оформления выдачи. Повторная выдача книги без доступных экземпляров получает 409 и показывает сообщение сервера.
11. Проверяем загрузку с __delay=1500, ошибку с __fail=500, пустой поиск и остановку сервера. После запуска API кнопка «Повторить» восстанавливает список.
12. Выполняем анализатор, модульные/виджетные тесты, серверные проверки и release-сборку. Сохраняем снимки приложения и настоящей вкладки Network.

## Используемые эндпоинты

Все пути в таблице указаны относительно API_BASE_URL, по умолчанию http://localhost:8080/api.

| Метод | Эндпоинт | Назначение |
|---|---|---|
| GET | /__health | Проверка доступности сервера |
| GET | /books, /authors, /genres, /publishers, /readers | Страница данных с серверным отбором |
| GET | /ресурс/:id | Подробные сведения о записи |
| POST | /ресурс | Создание записи |
| PUT | /ресурс/:id | Изменение записи |
| DELETE | /ресурс/:id | Логическое удаление |
| DELETE | /ресурс/:id?hard=true | Физическое удаление |
| POST | /ресурс/:id/restore | Восстановление |
| POST | /ресурс/bulk-delete | Массовое логическое удаление, тело ids |
| POST | /auth/login | Получение токена по учебному логину и паролю |
| POST | /auth/logout | Завершение сессии на сервере |
| GET | /publishers/:id/options | Компактные связи для каскадного выбора |
| POST | /loans | Выдача книги: bookId, readerId, days |
| POST | /loans/:id/return | Возврат экземпляра, поддержан репозиторием выдач |

Параметры списка: search, sort, page, size, includeDeleted и filter. У книг дополнительно передаются genreId, publisherId, yearFrom, yearTo. Учебные __fail и __delay доходят до сервера; ошибка 500 в рабочем режиме вызывается ответом API.

На запись книги отправляются publisherId, authorIds и genreIds; ответ содержит publisher, authors и genres. Book.fromJson разбирает оба представления. Служебные id, createdAt, deletedAt и copiesAvailable не отправляются при создании/изменении. Reader.card отправляется вложенным объектом без назначаемого сервером id.

## Схема обработки ошибок

~~~mermaid
flowchart TD
    A[Запрос Dio] --> B{Есть HTTP-ответ?}
    B -->|Да| C[Интерсептор: код и тело ответа]
    C --> D[Собственное ApiException]
    B -->|Нет| E[guard: сеть, таймаут или отмена]
    E --> D
    D --> F[Состояние списка, карточки или формы]
    F --> G[422: ошибки под полями]
    F --> H[409 и остальные ошибки: понятное сообщение]
    F --> I[Отмена: старый ответ игнорируется]
~~~

| Ситуация | Исключение | Отображение |
|---|---|---|
| 400 | BadRequestException | Сообщение о неверном запросе |
| 401 | UnauthorizedException | Предложение войти в API |
| 403 | ForbiddenException | Недостаточно прав |
| 404 | NotFoundException | Для карточки репозиторий возвращает null, показывается отсутствие записи |
| 409 | ConflictException | Сообщение о конфликте, например отсутствие экземпляров |
| 422 | ValidationException | Словарь errors попадает в поля формы |
| 5xx | ServerException | Сообщение сервера и возможность повтора |
| Сеть / CORS / таймаут | NetworkException | Подсказка о соединении, сервере и CORS |
| CancelToken | RequestCancelledException | Не показывается как ошибка списка |

Автоматически повторяются только GET при NetworkException: всего до трёх попыток, паузы 300 и 600 мс. HTTP 422, 409, 500, отмена и операции записи не повторяются автоматически. Ручная кнопка повтора остаётся доступной после ошибки чтения.

## Встреченная ошибка CORS

При проверке клиент был открыт по адресу http://127.0.0.1:5555, а сервер запущен с --origin http://localhost:5555. API отвечал на /__health, однако браузер не разрешал приложению прочитать ответы: источник страницы и Access-Control-Allow-Origin не совпадали. В приложении отображалась NetworkException с подсказкой проверить CORS.

Причина установлена сравнением адреса страницы и разрешённого сервером источника. После открытия клиента по http://localhost:5555 каталог загрузился без изменения клиентского сетевого кода. Для воспроизводимого запуска в командах клиента и сервера используется localhost и фиксированный порт 5555. OPTIONS возвращает 204, разрешённые методы и заголовки Content-Type, Authorization; это дополнительно проверено серверным тестом.

Снимок 09 показывает ошибку при несовпадении источников. Правильный запуск не требует отключения защиты браузера или расширения CORS.

## Изменения существующих экранов

Разметка списков, таблиц и основной формы ПР3 сохранена. Выбор реализации выполняется в main.dart и LibraryRepositories. Виджеты используют прежние классы состояния; Dio находится в core и repositories.

В CatalogScreen добавлены передача учебных параметров и вызов отмены старого поиска. В общей форме добавлены индикатор ожидания каскадного запроса и блокировка сохранения на это время. В навигационную оболочку добавлена кнопка входа; в карточку книги — переход к дополнительному экрану выдачи. Эти изменения обеспечивают новые действия и асинхронные состояния, а не выполнение HTTP из виджетов.

Уникальность в режиме API проверяет сервер: клиентский кэш не содержит весь каталог книг и читателей. Проверки формата и обязательности остаются на клиенте. Локальные репозитории сохранены для регрессионных тестов ПР2–ПР3.

## Исправления учебного сервера

В исходном mock-server.js normalize для readers отбрасывал card, а фильтры справочников и сортировка по сроку билета не применялись. В проектной копии это исправлено. Также перенесены проверки используемых связей при удалении и добавлен /publishers/:id/options, который возвращает только идентификаторы доступных авторов/жанров.

Подробный перечень дополнений приведён в api/README.md. Учётные записи и основные CRUD-эндпоинты исходного контракта сохранены.
