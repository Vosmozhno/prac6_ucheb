# Практическая работа №6

**Тема:** Адаптивная вёрстка, сборка, публикация и тестирование.

**Цель работы:** адаптировать приложение библиотеки к разным размерам экрана, проверить его работу, уменьшить релизную сборку и настроить автоматическую публикацию.

## Ход работы

1. Настраиваем адаптивную навигацию приложения. При ширине меньше 600 пикселей разделы располагаются на нижней панели, от 600 — на компактной боковой панели, а от 1100 — на боковой панели с подписями.

   **Скрин кода:** `lib/widgets/library_scaffold.dart`, метод `build`: `LayoutBuilder`, условия `phone` и `extended`, выбор `NavigationBar` и `NavigationRail`.

   Рисунок 110 – Адаптивная навигация приложения

2. Добавляем общий компонент адаптивной сетки. Он рассчитывает ширину карточек по доступному пространству: на телефоне используется одна колонка, на планшете — две, на широком экране — три.

   **Скрин кода:** `lib/widgets/adaptive_grid.dart` целиком, включая расчёт `columns` и `width`.

   Рисунок 111 – Расчёт количества колонок и ширины карточек

3. Проверяем представление каталогов на разных экранах. При ширине меньше 1100 пикселей используем карточки, на широком экране — общую таблицу. Длинные названия ограничиваем двумя строками, сохраняем прокрутку таблицы по двум направлениям.

   **Скрин кода:** `lib/screens/catalog_screen.dart`, метод `_content`: карточки с `maxLines` и `TextOverflow.ellipsis`, затем `EntityTable`. Прокрутка находится в `lib/widgets/entity_table.dart`.

   Рисунок 112 – Карточки и таблицы для разных размеров экрана

4. Проверяем ограничения ширины рабочей области и форм. Основное содержимое ограничено 1320 пикселями, формы сущностей — 1040. Поля формы перестраиваются с учётом доступной ширины и не растягиваются на весь монитор.

   **Скрин кода:** `lib/screens/entity_form_screen.dart`, метод `_fields` и `ConstrainedBox(maxWidth: 1040)`. Общее ограничение находится в `lib/widgets/library_scaffold.dart`.

   Рисунок 113 – Ограничение размеров форм и рабочей области

5. Проверяем расположение поиска и фильтров. Для переноса элементов используем `Wrap`, подпись переключателя может занимать несколько строк. На телефоне фильтры сворачиваются в `ExpansionTile`, освобождая место для списка записей.

   **Скрин кода:** `lib/screens/catalog_screen.dart`, метод `_toolbar` и блок `ExpansionTile`. Расположение полей фильтров — в `lib/widgets/book_filters.dart`.

   Рисунок 114 – Адаптация панели поиска и фильтров

6. Создаём начальный экран загрузки в HTML. Пока запускается Flutter, пользователь видит название библиотеки и индикатор. После первого кадра заглушка удаляется, а при ошибке загрузки появляется кнопка повтора.

## Сборка и измерения

Обычный вариант:

```bash
flutter build web --release --base-href /prac6_ucheb/ --dart-define=API_BASE_URL=https://prac6-library-api.onrender.com/api --no-web-resources-cdn
```

Вариант WebAssembly с JavaScript для браузеров, которые его не поддерживают:

```bash
flutter build web --release --wasm --base-href /prac6_ucheb/ --dart-define=API_BASE_URL=https://prac6-library-api.onrender.com/api --no-web-resources-cdn
```

После окончательной обычной сборки:

```bash
python3 tool/prepare_web.py
node tool/serve_web.js --base /prac6_ucheb/ --port 5555
```

Открываем `http://localhost:5555/prac6_ucheb/`. Для локального API используем при сборке `--dart-define=API_BASE_URL=http://localhost:8080/api` и запускаем `node api/mock-server.js --port 8080 --origin http://localhost:5555`.

| Вариант | Размер поставки, МиБ | Первый кадр, мс | Передано до первого кадра, МиБ |
| --- | ---: | ---: | ---: |
| Обычная JS-сборка до оптимизации | 36.18 | 140.3 | 8.98 |
| WebAssembly + JavaScript | 38.76 | 102.3 | 6.55 |
| JS-сборка после оптимизации | 16.99 | 147.8 | 8.73 |

Размер итоговой поставки уменьшился на **53.0%** по сравнению с обычной сборкой до оптимизации.


Размер означает сумму размеров всех файлов поставки, а не только JavaScript. После оптимизации учитывается результат `prepare_web.py`, включая `404.html`. Передано — ресурсы до первого кадра без HTML, измеренные браузером.

Время измерялось на этом компьютере во встроенном Chromium 156, по локальному HTTP без ограничения скорости и с `Cache-Control: no-store`. Для каждого варианта выполнено три загрузки, в таблице указана медиана. Измеряется экран входа, без ожидания запросов каталога. Эти числа не являются оценкой скорости произвольного интернет-соединения; внутренний кэш компиляции браузера может сохраняться между запусками.

Подробности: [browser-measurements.json](practice6/browser-measurements.json), [build-measurements.json](practice6/build-measurements.json). В записи Wasm подтверждены загрузки `main.dart.wasm` и `skwasm.wasm`, то есть сравнивался именно Wasm-режим.

Для измерений у всех вариантов использован одинаковый локальный API_BASE_URL; в опубликованной сборке GitHub Actions подставляет HTTPS-адрес Render. Локальное время первого кадра после оптимизации не улучшилось, при этом уменьшились поставка и объём передачи.

Шрифты уменьшились с 514 500 до 244 140 байт. Исходные шрифты и лицензия сохранены в `tool/fonts-original`; подмножества создаются `tool/subset_fonts.py`. Отдельные разделы вынесены в дополнительные JavaScript-модули, а из поставки удалены только файлы рендереров, которые обычная JS-сборка не запрашивает, и отладочные символы. Сокращение файлов поставки не означает такого же сокращения трафика: неиспользуемые файлы и раньше не загружались при открытии страницы.

## Настройки размещения

На GitHub Pages выбран источник **GitHub Actions**, задана переменная `API_BASE_URL`, путь сборки — `/prac6_ucheb/`. Скрипт подготовки создаёт `404.html` как копию `index.html` и `.nojekyll`. При обращении к внутреннему адресу Pages отдаёт HTML приложения вместо стандартной страницы ошибки, после чего адрес разбирает Flutter Router. Сам HTTP-ответ такого резервного документа на Pages имеет статус 404 — это особенность выбранного в методичке способа; пользователь видит работающий экран приложения. Локальный сервер проверки использует SPA fallback с ответом 200.

API размещён как **Node Web Service, Free**. `HOST=0.0.0.0` позволяет Render направлять запросы к процессу, `PORT` выдаётся платформой, `ALLOWED_ORIGIN=https://vosmozhno.github.io` разрешает CORS для клиента. В источник CORS не включается `/prac6_ucheb/`: origin содержит схему и домен. Ключ подписи генерируется Render через `generateValue: true`. Клиент и API работают по HTTPS, поэтому смешанного содержимого нет.

Бесплатный экземпляр Render может засыпать. Его пробуждение занимает до 50 секунд и более, поэтому первый запрос иногда завершается тайм-аутом; после пробуждения достаточно повторить вход или загрузку. Данные учебного API хранятся в памяти и возвращаются к исходным после перезапуска сервиса. Для изменения серверного кода у публично подключённого репозитория может потребоваться Manual Deploy в Render; автоматическая публикация клиента выполняется GitHub Actions при push в `main`.

Проверка автопубликации: https://github.com/Vosmozhno/prac6_ucheb/actions/workflows/pages.yml
